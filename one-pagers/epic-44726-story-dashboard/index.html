The epic was restructured in early June: automated testing was promoted to its own feature, a Future Scope feature now holds deferred work, and a Route to Production feature gathers the deployment work — its original pipeline story (45960) is now Done under the Platform team, and it has grown into a full Azure deployment breakdown covering Key Vault and secrets, a DbUp migration runner, Azure Files image storage, App Service hardening, observability, auth, and CI/CD — those deployment stories have each been decomposed into delivery tasks, around sixty in total, from ingress and secret-delivery decisions through to slot-swap promotion. Route to Production also carries a Platform-team workstream — the API repository set-up, access and permissions, App Service Terraform, Azure File Sync, an on-prem sync agent, a .NET 9 build pipeline, the deployment pipeline, and connectivity and security. Under the field-app feature, production-parity stubs mirror the RP sign-off, mapping, offline mapping, workforce, and in-app audit work alongside the login and work-order stubs, and scope stories cover feature flags to hide non-MVP surfaces, photo limits and image size, a photo gallery, job-versus-man hours, and sign-off questions.

This is the busiest cycle since the field-trial defect sweep: seven state changes and one reassignment, with no stories added and none removed. The field app moved furthest. Log in and permissions (45887) cleared QA and became the first field-app story to reach Ready to Deploy. Behind it, multi-team work-order visibility and completion (45889) and record work per span (45890) both came out of Awaiting QA into QA, so the QA band is now three field-app stories plus the on-prem API work. Two long-standing blocks broke on the same cycle: the on-hold reason story (46296) came off Blocked into Awaiting QA, and the CI/CD pipeline (47039) left Blocked for In Development with Keerthi Jagarlamudi — each after three cycles in that band. The update-notification defect (48554) closed to Done, the twenty-seventh Done item on the epic. Technical documentation (45899) was taken up into development by Mark Bissett, the only one of the four documentation stories to move. The single reassignment is the Woodplan RP-sheet story (45962), which passed from Ruth Havis to Mark Bissett while staying Blocked. Blocked therefore falls from six to four and In Development rises to seven. The backlog holds at 95 items for a fourth cycle.

The previous cycle recorded two state changes, both on Route to production, and nothing else. Log ingestion into Elasticsearch (48971) cleared development and closed to Done with Ross Bishop. Against that, the map-tile blob storage story (49066) went the other way, out of In Development into Blocked with Keerthi Jagarlamudi, where it still sits. The cycle before that was quieter again: view assigned work (45888) moved from Awaiting QA into QA, and 49066 was picked up from Ready to Play into In Development — the move that then reversed.

Before that came the largest cycle since the June restructure: fourteen states moved, twenty-five items changed owner and three stories were added. The nine field-trial defects all moved at once — 48555 fixed and Done, 48559, 48560 and 48561 fixed and into Awaiting QA, 48554 into QA, 48557 into Blocked, 48558 and 48562 removed — leaving only the photo capture and upload failure (48556) unstarted. Crash analytics (48089) closed to Done. Against that, the Woodplan RP-sheet creation logic (45962) came out of QA into Blocked and passed to Ruth Havis, and the CI/CD pipeline story (47039) left refinement for Blocked with its eight delivery tasks still open.

The three stories added in that cycle all sit under Route to production and all lie outside the Android repo. 48971, log ingestion into Elasticsearch, is now Done; it pairs with observability and operations (47037), whose telemetry-SDK task names Elasticsearch as the target and which remains In Development. 49066 and 49067 are a pair: add a map-tile blob container to the Canopy API storage account, then serve tiles from it through the API. Both are now stalled — 49066 in Blocked, 49067 at Ready to Play with Mark Bissett. Together they are the hosted tile source that offline mapping (45988) and the blocked map download (48557) have been waiting on, so the block on 49066 holds up that chain as well. The Android side already has the PMTiles archive and tile-server stack built and unit-tested against it.

The bands now stand at seventeen Awaiting QA, four In QA, seven In Development, eight Ready to Play, twenty-seven Done, four Ready to Deploy and four Blocked, with fourteen items still in refinement, four removed and three spikes closed. The QA band has turned over completely in composition but not in size: it now holds view assigned work (45888), multi-team visibility and completion (45889), record work per span (45890) and the on-prem API implementation (46887), which is the longest-running item in it. In Development grows to seven — the test environment set-up (45912), the automated-testing deliverable (45957), observability and operations (47037), auth and security hardening (47038), the feature-flag work (48591) and, new this cycle, the CI/CD pipeline (47039) and technical documentation (45899). Ready to Deploy grows to four: support platform with deployment (46608), App Service hosting hardening (47036), the Lead Team flag story (45881) and now login and permissions (45887). Blocked falls to four — 45962, 46886, 48557 and 49066 — its smallest since the field-trial sweep. Feature flags remain duplicated and both halves remain live: 48591 In Development over the same ground as 46585, already Awaiting QA.

The wider standing from the June restructure holds. On the field-app and back-end side the built work still sits in a broad Awaiting QA band — mapping, workforce recording, RP sign-off, offline mapping, the photo and sign-off scope stories and the in-app audit work among them — though multi-team work-order visibility and record-work-per-span have now moved on into QA. Across Route to Production, Key Vault and secrets, the DbUp database migration runner, the .NET 9 API build pipeline, the on-prem sync agent, the API repository set-up, repository access and permissions, platform configuration, the App Service Terraform, Azure File Sync, the shortened file-sync cadence, the Platform deployment pipeline, the health-check endpoint fix, the Elasticsearch log-ingestion investigation, the two Google Play testing stories, and the deployment-pipeline story that seeded the feature (45960) are all Done. Connectivity, security and access (47229) and the production Google Play listing (48092) remain in refinement; the CI/CD pipeline story (47039) has come off Blocked into development after three cycles there; and the DbUp migration runner (47033) is Done with its six delivery tasks still open beneath it, alongside the closed DbUp bug (48081). The Future scope feature (46327) sits under a separate epic, 47619 Future Scope (V2 onwards), so the deferred cost-uplift story and the soft-delete spike belong to a V2 epic and are shown here for continuity only. The test strategy and the ARB presentation are Done, the two QA execution stubs for the field app and the app-to-Woodplan route sit at Ready to Play, three of the four documentation stories hold at Ready to Play with the technical one (45899) now in development, and the standalone Woodplan back-end test stories have been removed.

Coverage is reported here from the current working branch, Dev, exactly as it stands in the tree. This branch carries 111 JVM unit tests across 23 files — completion question, audit, dictation, operational-info and photo-limit rules, the map feature mappers, UI-state reducers, camera-safety and location-fix logic and offline state, the offline map pack, PMTiles archive and tile-server stack, the on-prem API client configuration, sync-summary and session-token logic, the app-update URL validator, debug-build guards, time utilities, the financial-password verifier, and an annotation-editor saved-state audit. Two instrumented test files, the Room database migration test and the sample instrumented test, sit alongside them. Dev has taken no commits since 30 July, so the tree behind these chips is the same tree the last seven dashboards reported, and every movement recorded in this refresh is a board movement rather than a code one. Honest caveat: the six ViewModel suites (login, operative selection, work-order list, work-order overview, completion and map) and the Maestro UI flow suite are not present on Dev, so no story carries a Maestro chip and the unit chips reflect the logic and infrastructure suites that are actually in the tree. Those suites have not been lost — the Testing branch still holds 27 Maestro flow files, being 14 authored Android flows, nine iOS flows and four shared login and operative-selection subflows, alongside the six ViewModel suites, which carry 63 tests between them (completion 14, map 14, work-order list 12, work-order overview 12, login 6, operative selection 5). Both figures are unchanged from the previous dashboard. Those flows are authored to run in CI, cannot be exercised on this machine, and are not on the branch the app is being built from, so they are reported here as absent rather than as coverage. The JVM suite still has not been run on this host, and the gap has widened: a JDK is present (OpenJDK 26), but this cycle there is no Android SDK on the machine at all — no SDK directory, no platform or build-tools packages and no local.properties — so Gradle cannot reach the test task. The suites in the tree therefore await their first recorded run on this branch.
