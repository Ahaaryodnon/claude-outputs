The epic was restructured in early June: automated testing was promoted to its own feature, a Future Scope feature now holds deferred work, and a Route to Production feature gathers the deployment work — its original pipeline story (45960) is now Done under the Platform team, and it has grown into a full Azure deployment breakdown covering Key Vault and secrets, a DbUp migration runner, Azure Files image storage, App Service hardening, observability, auth, and CI/CD — those deployment stories have each been decomposed into delivery tasks, around sixty in total, from ingress and secret-delivery decisions through to slot-swap promotion. Route to Production also carries a Platform-team workstream — the API repository set-up, access and permissions, App Service Terraform, Azure File Sync, an on-prem sync agent, a .NET 9 build pipeline, the deployment pipeline, and connectivity and security. Under the field-app feature, production-parity stubs mirror the RP sign-off, mapping, offline mapping, workforce, and in-app audit work alongside the login and work-order stubs, and scope stories cover feature flags to hide non-MVP surfaces, photo limits and image size, a photo gallery, job-versus-man hours, and sign-off questions.

This is a triage cycle. The nine field-trial defects raised last cycle (48554 to 48562) have all been picked up: every one now carries an owner — eight to Mark Bissett and the photo capture and upload failure (48556) to Aaron Haydon — and seven have moved from New to Ready to Play. Only the two map defects remain New, the unavailable map download (48557) and the map not recentring on the current location (48558), and both are now assigned. One story was added, taking the backlog from 90 to 91: 48591, feature flag off non-MVP features, sits under the field-app feature at Ready for Refinement. It covers the same ground as 46585, implement feature flags to hide non-MVP features, which is already Awaiting QA, so the two want de-duplicating before either is played.

Three stories moved into or through QA. Crash analytics (48089) went from In Development to In QA, and the on-prem API implementation (46887) came off Blocked into In QA, so the In QA band grows from one story to three alongside the Woodplan RP-sheet creation logic (45962). The Blocked band eases from four to three: the on-hold reason for Actions (46296) and the on-prem image storage story (46886) remain blocked, with the soft-delete spike outside the epic. Two stories reached Ready to Deploy — support platform with deployment (46608) from Ready to Play, and App Service hosting hardening (47036) from In Development — joining the Lead Team flag story (45881) and taking that band from one to three. Pull-request and branch governance (48094) closed out to Done. In Development therefore drops from seven stories to four: the test environment set-up, the automated-testing deliverable, observability and operations, and auth and security hardening. The Awaiting QA band holds at seventeen across the field-app and integration features, with no story entering or leaving it, so the defect sweep has yet to reach the band it will have to clear.

The wider standing from the June restructure holds. On the field-app and back-end side the built work sits in a broad Awaiting QA band — multi-team work-order visibility and completion, record-work-per-span, mapping, workforce recording, RP sign-off and the in-app audit work among them. Across Route to Production, Key Vault and secrets, the DbUp database migration runner, the .NET 9 API build pipeline, the on-prem sync agent, the API repository set-up, repository access and permissions, platform configuration, the App Service Terraform, Azure File Sync, the shortened file-sync cadence, the Platform deployment pipeline, the health-check endpoint fix, the two Google Play testing stories, and the deployment-pipeline story that seeded the feature (45960) are all Done. Connectivity, security and access (47229) and the production Google Play listing (48092) remain in refinement, as does the CI/CD pipeline story (47039); the DbUp migration runner (47033) is Done with its six delivery tasks still open beneath it, alongside the closed DbUp bug (48081). The Future scope feature (46327) sits under a separate epic, 47619 Future Scope (V2 onwards), so the deferred cost-uplift story and the soft-delete spike belong to a V2 epic and are shown here for continuity only. The test strategy and the ARB presentation are Done, the two QA execution stubs for the field app and the app-to-Woodplan route sit at Ready to Play, the four documentation stories are unchanged at Ready to Play, and the standalone Woodplan back-end test stories have been removed.

Coverage is reported here from the current working branch, Dev, exactly as it stands in the tree. This branch carries 111 JVM unit tests across 23 files — completion question, audit, dictation, operational-info and photo-limit rules, the map feature mappers, UI-state reducers, camera-safety and location-fix logic and offline-state, the offline map pack, PMTiles archive and tile-server stack, the on-prem API client configuration, sync-summary and session-token logic, the app-update URL validator, debug-build guards, time utilities, the financial-password verifier, and a new annotation-editor saved-state audit. Two instrumented test files (the Room database migration test and the sample instrumented test) sit alongside them. Honest caveat: the six ViewModel suites (login, operative selection, work-order list, work-order overview, completion and map) and the Maestro UI flow suite are not present on Dev, so no story carries a Maestro chip this cycle and the unit chips reflect the logic and infrastructure suites that are actually in the tree — the suite is steady at 111 tests across 23 files, unchanged since the previous dashboard — the branch has taken no commits since then, so the tree behind these chips is the same tree the last dashboard reported. Those suites have not been lost: the Testing branch still holds 27 Maestro flow files — 14 authored Android flows and nine iOS flows plus four shared login and operative-selection subflows — alongside the six ViewModel suites, which carry 63 tests between them. Both figures are unchanged from the previous dashboard. They are authored to run in CI and cannot be exercised on this machine, and they are not on the branch the app is being built from, so they are reported here as absent rather than as coverage. There is still no JDK on the build host, so the JVM suite was not re-run here — the suites in the tree await their first run on this branch. The in-app audit story does carry a CompletionAuditRules suite and a resubmission flow behind it.
